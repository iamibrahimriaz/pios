# Best Practices

---

# 1. Write the First Build Line Before Anything Else

For each option, state what would be built first, in one line, before describing the
option in full.

Three options whose first-build lines match are one option. Catching that at the start
saves generating three full descriptions of the same idea.

---

# 2. Write the Advocate Sentence for Every Option

One honest sentence making the case *for* each — including the ones you expect to reject.

If it cannot be written, the option is decoration. Replace it before continuing.

---

# 3. Score the Weights Before Seeing the Options

Assign criterion weights based on what the research established, then score.

Weighting after the options are visible lets the weights drift toward whichever criterion
favors the preferred answer.

---

# 4. Write the Rejection Column First

Fill in "what we lose by rejecting this" before writing why the chosen option won.

Working in that order produces honest rejection notes. Working the other way produces
rejections written to make the choice look better.

---

# 5. Walk the Workflow, Do Not Assert the Test

Take the numbered workflow from module 03 and mark each step against the capabilities
above the line.

A written walk is checkable. "The MVP covers the core job" is a claim, and it is usually
made by someone who did not walk it.

---

# 6. Cut Until It Hurts, Then Check It Still Works

The instinct is to include everything that scored well. That produces a ranked list, not
a cut.

Remove capabilities until the end-to-end test fails, then add back the last one. That is
the line.

---

# 7. Record the Hardest Thing You Cut

Name the capability that was most difficult to leave out, and why it went.

That note is what stops it returning as an unargued addition in month three, and it tells
the operator where the cut was genuinely painful.

---

# 8. Write "What This Does Not Prove" in the Same Breath

Immediately after writing what the MVP proves, write what it leaves unanswered.

Later, when adoption is weaker than hoped, that line is what prevents the team concluding
the wrong thing.

---

# 9. Pull Non-Goals From Module 04

The excluded problems are already identified there as real and out of scope.

Restating them as non-goals converts an implicit omission into a deliberate refusal, which
is what non-goals are for.

---

# 10. Rate Likelihood With the Impact Column Covered

Literally: assess how likely each risk is before looking at what it would cost.

Assessing them together anchors probability to comfort — the worse the consequence, the
lower the likelihood people assign.

---

# 11. Write the Early Warning Before the Mitigation

The warning sign forces the mechanism to be articulated. Once the mechanism is clear, the
mitigation is usually obvious, and often different from the first one that came to mind.

---

# 12. Run a Pre-Mortem Before Finalizing the Register

Eighteen months out, the product failed. Write why.

It reliably surfaces commercial and organizational risks that a forward-looking register
misses, because forward registers are written by people thinking about the plan working.

---

# 13. Diff Your Language Against the Source Modules

Read the strategy alongside modules 04, 05 and 06.

Anywhere this document sounds more certain than they did, change it back. This is the
single most effective check in the module and takes ten minutes.

---

# 14. Give the Operator Options, Not a Conclusion

The checkpoint section should contain decisions with recommendations — "approve the cut as
drawn / expand to include X at a cost of «n» weeks / narrow further" — not a summary of
what was decided.

A checkpoint offering one option is a status report.

---

# 15. Say the Uncomfortable Thing in the First Paragraph

If the problem is unproven, the gap is undefensible, or viability is conditional, that
belongs in the checkpoint's opening lines.

Placed at the end, it reads as a caveat. Placed at the start, it is what the operator is
actually deciding about.

---

# Anti-Practices

| Habit | Why it fails |
| --- | --- |
| Options written after the choice | The module documents rather than decides |
| Straw-man alternatives | The count is met, the purpose is not |
| Weights set after scoring | The criteria bend toward the preferred answer |
| MVP as a ranked list | No cut; no learning |
| End-to-end test asserted | Usually false when actually walked |
| Non-goals omitted | Scope creep with no baseline |
| Uniform risk ratings | Register is never used |
| Confident restatement of uncertain inputs | Laundering |
| Checkpoint as announcement | Removes the decision from the decider |

---

# Self Assessment

- Did I write first-build lines before full descriptions?
- Can I advocate for every option I rejected?
- Were weights fixed before scoring?
- Did I write rejections before justifications?
- Did I walk the workflow on paper?
- Did I cut until it broke, then add one back?
- Did I record the hardest cut?
- Did I write what the MVP does not prove?
- Did I rate likelihood independently of impact?
- Did I diff my language against modules 04–06?
- Does my checkpoint offer a choice?

---

> **Practice Principle**
>
> Most of these practices are about doing things in a particular order.
>
> Strategy work goes wrong mostly by sequence: deciding first, then
> assembling the reasoning that makes the decision look inevitable.
