# Learning Objectives

---

# Overview

> After this module you should be able to rank problems on evidence you can point to,
> tell the difference between something you observed and something you concluded, and
> say "we do not know this yet" in a form that travels.

The third clause is the one people find hardest and the one the framework most needs.

---

# Knowledge Objectives

You should understand:

- The three scoring axes — frequency, severity, current workaround — and why frequency
  is usually underweighted
- What counts as `[verified]`, what is `[inferred]`, and what is `[assumption]`
- Why a workaround is the strongest evidence available before launch
- What `declared_shortfall` is, when it is permitted, and what it obliges downstream
- The difference between a symptom and a root cause
- What a validation plan is for — resolving a specific uncertainty, not "learning more"

---

# Thinking Objectives

The shift is from *is this a problem* to *what do I actually know about it*.

Instead of asking:

> "Is this a real problem?"

ask:

- How often does it happen, and to whom?
- What do they do about it today, and what did that cost them to build?
- Which piece of this did I see, and which did I conclude?
- If I am wrong about this, what else falls over?
- What single observation would settle it?

The last question is the validation plan in miniature.

---

# Skill Objectives

You should be able to:

- Write a problem statement with no solution in it
- Score on all three axes with the evidence for each score attached
- Identify a workaround and read it as a specification
- Separate a symptom from what causes it
- Declare a shortfall in a form module 07 can act on
- Write a validation plan whose steps could produce a disconfirming result

---

# Analytical Objectives

You should develop the ability to:

- Notice when a "verified" problem is an interview quote about a hypothetical
- Detect a ranking produced to justify a solution already chosen
- Recognize a problem that is real, painful, and already adequately solved
- Distinguish problems the user has from problems the user's organization has

---

# Judgment Objectives

**Which problem is the sharpest.** The gate requires one to be identified and defended.
The defense should rest on evidence, not on which one is most interesting to solve.

**When to declare a shortfall.** Too eagerly and it becomes an excuse; too reluctantly
and inference gets promoted. The test: if you cannot point to a specific observation
supporting a problem, it is not verified — regardless of how confident you are.

---

# You Have Learned This When

| Signal | What it indicates |
| --- | --- |
| You ask "what do they do about it now" before "how bad is it" | The workaround habit has formed |
| An empty verified list does not feel like a failed run | The shortfall mechanism is understood rather than avoided |
| You can name which of your problems is inference | The distinction is live, not theoretical |
| You rank a frequent mild problem above a rare severe one and can defend it | The axes are doing real work |
| Your validation plan could disprove your favorite problem | It is a plan rather than a formality |

---

# What This Module Does Not Teach You

It does not teach solution design — that is module 07, and the three-module gap between
them is deliberate. It does not teach interviewing; that is a module 03 skill applied
here. It does not tell you whether a validated problem is worth a business, which needs
modules 05 and 06.

---

> **Objectives Principle**
>
> The skill this module teaches is the ability to write down what you do not know, in
> a form that makes someone else act differently.
>
> Everything else here is bookkeeping around that one capability.
